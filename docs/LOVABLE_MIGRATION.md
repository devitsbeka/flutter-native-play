# Removing the Lovable dependency

What the platform was doing for us, what replaced it, and the external
configuration required before this can ship.

## What was coupled to Lovable

| Area | Before | After |
| --- | --- | --- |
| Social login | `@lovable.dev/cloud-auth-js` proxied Google/Apple OAuth and handed back tokens | `supabase.auth.signInWithOAuth` directly (`src/integrations/oauth.ts`) |
| AI content generation | 34 edge functions hard-coded `ai.gateway.lovable.dev` + `LOVABLE_API_KEY` | `supabase/functions/_shared/ai.ts` picks a provider from secrets |
| Build tooling | `lovable-tagger` Vite plugin | removed |
| CORS allowlist | any `*.lovable.app` / `*.lovableproject.com` origin | exact-match allowlist + `CORS_EXTRA_ORIGINS` |
| Referral links | pointed at `flutter-native-play.lovable.app` | `SITE_URL` (`src/config/site.ts`), defaults to `https://mytrivia.io` |
| Social preview image | `flutter-native-play.lovable.app/og-image.png` | `mytrivia.io/og-image.png` |
| App identity | bundle id `app.lovable.f54c9281…`, app name "World Quizzes" | `io.mytrivia.app`, "MyTrivia" |
| Lockfile | `bun.lock` pinned Lovable's private registry, so `bun install` failed | regenerated, resolves from public npm |

## Required before deploying

### 1. Enable OAuth providers in Supabase — blocks social login

The app now asks Supabase for OAuth instead of routing through Lovable's
proxy, so the providers must exist on the Supabase project itself.

In **Authentication → Providers**:

- **Google** — create an OAuth client in Google Cloud Console (Web
  application), then paste the client ID and secret. Add
  `https://sqwpzezkhpqkdyltvsim.supabase.co/auth/v1/callback` as an
  authorized redirect URI.
- **Apple** — needs a Services ID, a Sign in with Apple key (.p8), the Team
  ID and Key ID from the Apple Developer account. Same callback URL.

In **Authentication → URL Configuration**, set Site URL to
`https://mytrivia.io` and add every origin that should be allowed to
return from a login: `https://www.mytrivia.io`, `http://localhost:5173`,
`http://localhost:8080`, and `capacitor://localhost` for the native shell.

Apple is likely already configured — native iOS sign-in already calls
`supabase.auth.signInWithIdToken({ provider: "apple" })`, which only works
with the Apple provider enabled. Google is the one to verify.

**Verify before merging:** on a preview deploy, click Google sign-in and
Apple sign-in. `"Unsupported provider: provider is not enabled"` means the
dashboard step is missing.

### 2. Set an AI provider secret — not blocking, but finishes the job

`_shared/ai.ts` resolves a provider at cold start, first match wins:

1. `AI_GATEWAY_URL` + `AI_GATEWAY_API_KEY` — any OpenAI-compatible endpoint
   (OpenRouter, Azure, a self-hosted proxy). Set `AI_MODEL_PREFIX=""` if the
   gateway wants bare model names.
2. `GEMINI_API_KEY` — Google AI Studio's OpenAI-compatible endpoint. All 34
   functions already request `google/gemini-*` models, so this is the
   closest match to current behavior; the `google/` prefix is stripped
   automatically.
3. `LOVABLE_API_KEY` — the legacy gateway, still honored so production keeps
   working until step 1 or 2 is done.

To cut over: `supabase secrets set GEMINI_API_KEY=...`, redeploy the
functions, confirm generation still works from the admin tools, then delete
the `LOVABLE_API_KEY` secret and the legacy branch in `_shared/ai.ts`.

**Watch the image models.** `generate-cover-image`, `generate-question-image`
and `generate-avatar` use `gemini-*-image-preview` through chat completions.
Google's OpenAI-compatible endpoint handles image *input* fine, but image
*output* may need the native `generateContent` API. Test those three
functions specifically after cutover; if they fail, they are the only ones
needing a bespoke call rather than the shared constant.

### 3. Hosting

If the site is still served from Lovable's infrastructure, that is the last
runtime tie. The build is a stock Vite SPA (`npm run build` → `dist/`), so
Vercel, Netlify, or Cloudflare Pages will serve it with no code changes.
Set `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and optionally
`VITE_PUBLIC_SITE_URL` in the host's environment, and point `mytrivia.io`
at the new deployment.

## Also fixed along the way

- **Referral links were broken.** Invites generated by the friends modal
  pointed at `flutter-native-play.lovable.app`, so every link a player sent
  landed a friend on a preview domain instead of the real site.
- **CORS accepted far too much.** The allowlist matched with `startsWith`,
  so `https://mytrivia.io.example.com` passed as `https://mytrivia.io`, and
  a wildcard admitted every project on the old hosting platform. Both are
  now exact matches, with `CORS_EXTRA_ORIGINS` for preview deploys.
- **`npm test` was always red.** Vitest had no config and collected the
  Playwright specs in `e2e/`, which throw on import. Vitest now excludes
  `e2e/`, so the suite is a usable gate for the monorepo work ahead.

## Note on `supabase/migrations/`

Several migration files carry comments mentioning Lovable's security
scanner. Those are applied, immutable history and were deliberately left
alone — they describe why a policy exists and rewriting them would not
change anything at runtime.
